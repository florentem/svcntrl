# Svcntrl Architecture

В этом документе описаны ключевые технические и архитектурные решения мода Svcntrl.

## 1. Потоковая модель и асинхронность (Threading Model)

Minecraft Server работает в основном на одном потоке (Main Server Thread). Тяжелые операции с блоками могут вызывать сильные лаги (TPS drop). 
Svcntrl решает эту проблему через собственную систему `TaskScheduler` и гибридный подход к асинхронности:

- **Обработка блоков (Чтение/Запись):** Всегда происходит **только на главном потоке** (Main Thread), так как обращение к миру из других потоков вызывает `ConcurrentModificationException` и краши.
- **Дробление задач (TaskScheduler):** `SaveTask`, `RestoreTask` и `StartPreviewTask` реализуют интерфейс `TickTask`. В методе `tick()` они обрабатывают ограниченное количество блоков.
- **Ограничение по времени (Глобальный бюджет):** `TaskScheduler` выделяет общий бюджет 25 мс на один игровой тик. Этот бюджет динамически делится поровну между всеми активными фоновыми задачами. Если задача превышает свою долю времени, она приостанавливает работу (`return false`) и продолжает со следующего тика. Это решает проблему лагов (просадок TPS), когда одновременно запущено множество задач.
- **Атомарность операций и Блокировки:** Чтобы избежать повреждения данных, во время сохранения или восстановления проект блокируется флагом `project.isLocked()`. Любые параллельные команды управления и взаимодействия игроков с блоками в выделенной зоне (попытки сломать/поставить блок) автоматически отменяются, пока операция не завершится.
- **Ввод/Вывод (I/O) и Атомарная запись:** Сериализация в NBT, генерация JSON и физическая запись на диск (`Files.write`, `NbtIo.writeCompressed`) **строго вынесены в асинхронные пулы потоков** (`CompletableFuture.runAsync()`). Перед вызовом асинхронной записи, все мутабельные данные сериализуются в JsonObject на главном потоке. Запись JSON-файла проекта производится во временный файл `.tmp` с последующим атомарным переименованием (`StandardCopyOption.ATOMIC_MOVE`), чтобы предотвратить повреждение данных при внезапном отключении сервера.

## 2. Оптимизация работы с блоками

Главное «бутылочное горлышко» при работе с сотнями тысяч блоков — это поиск чанков и обновление освещения/соседей.
Svcntrl использует несколько критических оптимизаций:

- **Кэширование Чанков (Chunk Caching):**
  Вместо вызова `world.getBlockState(pos)`, который на каждый блок ищет нужный чанк в хэш-мапе, задачи (Save, Restore, Preview) кэшируют ссылку на `WorldChunk`. Запрос к миру происходит только при пересечении границы чанка (раз в 16 блоков). Это снижает нагрузку на CPU на 90-95%.

- **Флаги обновления блоков (`world.setBlockState`):**
  Во время восстановления (RestoreTask) блоки устанавливаются с флагом `Block.NOTIFY_LISTENERS | Block.FORCE_STATE | Block.SKIP_DROPS` (битовая маска `50`).
  - `FORCE_STATE` (16) — отключает обновление соседей и каскадные реакции (вода не течет мгновенно, редстоун не мигает во время установки).
  - `SKIP_DROPS` (32) — предотвращает выпадение предметов при перезаписи блоков инвентарей или руд.
  - `NOTIFY_LISTENERS` (2) — синхронизирует чанк с клиентом.

## 3. Управление сущностями (Entities & BlockEntities)

- **BlockEntities (сундуки, печки, спавнеры):** Сохраняются в отдельный NBT список при создании снапшота. При восстановлении сначала устанавливаются все блоки, затем, во второй фазе, ставятся BlockEntities, чтобы избежать крашей (когда NBT применяется к блоку воздуха).
- **Entities (рамки, картины, стойки для брони):** В 1.21.x сущности сохраняются с помощью `entity.saveSelfData()`. При восстановлении используется `EntityType.loadEntityWithPassengers`.
- **Превью сущностей:** Мод может показывать игроку несуществующие блоки через пакеты. Однако клиент не позволяет легко показывать "фейковые" сущности. Поэтому `PreviewManager` использует хак: он отменяет отправку пакетов спавна сущностей (в `ServerPlayNetworkHandlerMixin`), чтобы временно «скрыть» реальные сущности, находящиеся в зоне, пока включен режим превью.

## 4. Палитра и формат данных (V2 Format)

Чтобы сократить объем оперативной памяти и размер файлов на диске, Svcntrl использует V2 формат хранения (вдохновленный самой игрой и Litematica):
- Уникальные стейты блоков (BlockState) собираются в массив `Palette`.
- Сама зона сохраняется как плоский `int[] blockData`, где каждый элемент — это индекс в `Palette`.
- Координаты блоков не сохраняются в массив (индекс в `blockData` вычисляется по формуле: `x + y * width + z * width * height`).

## 5. Экспорт в Litematica

Litematica использует собственный формат `.litematic`. Svcntrl имеет транслятор (`ExportManager`), который на лету конвертирует внутренний формат V2 в структуру регионов Litematica (с соблюдением спецификации Litematica NBT, использованием `BitSet` для упаковки битов и правильным форматом `BlockEntities` и `Entities`). Экспорт полностью асинхронный и не влияет на TPS сервера.
